Claude Code を使い始めて少し経つのだが、`.claude/` というフォルダが何のためにあるのか、長らくよくわかっていなかった。サブエージェント、スラッシュコマンド、Skills、`settings.json`、それぞれ名前は聞いたことがあるけれど、自分のプロジェクトでどう配置すれば何が起きるのかがピンとこない。公式ドキュメントは長いし、全部読む前にとりあえず動くところまで持っていきたい。

そんな状態で、Zenn 記事を書きたいというモチベーションを起点に、`.claude/` の中身を一つずつ触ってみた。やってみたら、サブエージェントもスラッシュコマンドも Skills も、想像していたよりずっと素朴な仕組みで、Markdown を数枚置くだけで動いた。せっかくなので、同じところで詰まっている人の最短ルートになるよう、触ってわかったことを順番に書き残しておく。

## 1. やってみたゴール（先に成果物）

最終的にできたのは、Zenn 記事を書くときに次の 3 つのスラッシュコマンドを順番に叩けば一通り回る、という状態だ。

- `/09_insight_extractor`: 記事の構成案（タイトル候補・フック・章立て）を作るサブエージェントを呼び出す
- `/07_tech_writer {構成案ファイル}`: 構成案に沿って本文を執筆するサブエージェントを呼び出す
- `/review`: 書き上がった内容を Claude Code 組み込みの Skill でレビューする

Claude Code のプロンプト欄で `/` を打つと、自分が定義したスラッシュコマンドと、組み込みの Skills がずらっと候補として並ぶ。設定したのは `.claude/` 配下に Markdown を数枚置いただけで、本体の機能は何もいじっていない。これだけで「次は何を叩くか」が画面の上で完結するようになる。

ここまでの設定の流れを、後の章で順番にほどいていく。

## 2. `.claude/` フォルダの正体を整理する

最初にハマったのは、そもそも `.claude/` 配下のファイルが「誰が・いつ・どう解釈するのか」がわからなかったことだ。サブエージェントは知っているが、`commands/` というフォルダもあるし、`settings.json` と `settings.local.json` の使い分けもわからない。

触ってみてやっと理解できた全体像はこうだ。

| パス | 役割 | 誰が解釈するか |
|---|---|---|
| `.claude/agents/{name}.md` | サブエージェント定義 | Claude Code が認識して呼び出す |
| `.claude/commands/{name}.md` | カスタムスラッシュコマンド | Claude Code が `/` 入力時に検出 |
| `.claude/settings.json` | プロジェクトレベル設定（チームで共有） | Claude Code 起動時 |
| `.claude/settings.local.json` | 個人ローカル設定（gitignore 推奨） | 同上 |
| `~/.claude/` | ユーザー全体の設定（プロジェクト横断） | Claude Code |
| Skills（組み込み） | Claude Code 本体やプラグイン由来 | Claude Code |

ポイントは、**「自分で配置するファイル」と「Claude Code 本体に組み込まれた機能」は別物**だ、ということだった。私は最初、`/review` のような便利コマンドも自分で定義しないと使えないと思い込んでいて、そのせいで「何から書けばいいんだ」と固まっていた。実際は、組み込みの Skills だけでもかなり多くのことができる。

この全体像をうっすらでも握ってから、サブエージェント → カスタムスラッシュコマンド → Skills の順に触っていったら、迷子になる時間がだいぶ減った。以降の章はその順番でなぞる。

## 3. サブエージェント (`.claude/agents/`) を触ってみる

最初に試したのがサブエージェントだった。「専用の役割を持った Claude を別コンテキストで動かせる」と聞いて、難しそうな気がしていたが、実体は YAML frontmatter 付きの Markdown ファイルを 1 枚置くだけだった。

たとえば構成案を作る担当のサブエージェントは、こう書いた。

```markdown
---
name: 09_insight_extractor
description: 気づきを抽出してZenn投稿案（タイトル・フック・章立て）を作成。本文執筆は禁止。
---

# Insight Extractor エージェント

## 役割
気づきを抽出して Zenn の投稿案（構成案）を作る。

## 出力
- markdown ファイル: タイトル候補、フック、章立て、キーメッセージ

## 禁止事項（厳守）
- 記事本文の執筆（タイトル・フック・構成まで）
- 投稿の実行
```

これを `.claude/agents/09_insight_extractor.md` として保存するだけで、Claude Code が認識してくれる。同じパターンで本文執筆担当の `07_tech_writer.md` も配置した。

触ってみてわかった大事なことが二つある。

ひとつは、**サブエージェントは独立したコンテキストで動く**こと。メイン会話の履歴を引きずらないので、メインで雑談していても、サブエージェントは新鮮な状態で仕事を始める。これは思ったより便利だった。

もうひとつは、**「禁止事項」を書いておくと役割境界が安定する**こと。Claude は得意なことを勝手にやろうとするので、構成案担当に「本文の執筆禁止」と明記しないと、章のキーメッセージとして 1〜2 文の本文っぽいものを書いてきてしまう。明文化することで、出力がだいぶ落ち着いた。

## 4. スラッシュコマンド (`.claude/commands/`) で呼び出しを楽にする

サブエージェントは置いただけで使えるのだが、メイン会話から呼び出すには「`09_insight_extractor` サブエージェントを使って…」と毎回書く必要がある。これがすぐに面倒になった。

そこで `.claude/commands/{name}.md` に薄いラッパーを置いた。

```markdown
---
description: ⑦Tech Writer — Zenn 記事執筆エージェントを起動
argument-hint: [構成案ファイルのパス]
---

`07_tech_writer` サブエージェントを使って次の依頼を処理してください。サブエージェントの責務・禁止事項を必ず守ること。

依頼内容: $ARGUMENTS
```

これだけで、プロンプト欄に `/07_tech_writer data/insight_drafts/xxx.md` と打てばサブエージェントが起動する。`$ARGUMENTS` にはスラッシュの後ろに書いた文字列がそのまま入る。

地味に効くのが `argument-hint` だ。スラッシュコマンドを補完で選ぶときにヒントとして表示されるので、自分で何の引数を渡せばいいか忘れない。サブエージェントを増やしていくと「どのコマンドが何を期待するんだっけ」になるので、これは早めに書く癖をつけたほうがいい。

サブエージェントとカスタムスラッシュコマンドを 1 ペアずつ作っただけで、執筆フローは「`/09_insight_extractor` → 構成レビュー → `/07_tech_writer`」と、3 ステップに圧縮された。

## 5. Skills を発見した（`/init` `/review` `/security-review` ...）

Tech Writer まで作って一息ついたところで、ふと `/` を入力したときの補完を眺めていたら、自分が定義していないスラッシュコマンドが大量に並んでいることに気づいた。`/init` `/review` `/security-review` `/simplify` `/loop` `/schedule` などなど。

これが Skills だった。**Claude Code に最初から組み込まれている機能**で、`.claude/` を空っぽにしていても使える。

私が触ってみて便利だったのを挙げると、

- `/init`: プロジェクトを初めて開いたときに `CLAUDE.md` を生成してくれる
- `/review`: コードや記事の差分をレビューしてくれる
- `/security-review`: セキュリティ観点のレビューを走らせる
- `/loop`: 同じプロンプトを定期的に繰り返し実行する
- `/schedule`: cron で定期実行のエージェントを組む

サブエージェントを書く前にこれを見ていたら「自分で書くまでもない仕事」がいくつもあった。とくに `/review` は、自作の Tech Writer に書かせた記事の最終チェックにそのまま使えて、わざわざレビュー専用のサブエージェントを作る必要がなかった。

ちなみにこの記事自体も、Tech Writer サブエージェントに書いてもらった本文を、人間がちょこちょこ手で直したものだ。書きながら同時にデバッグしている感覚があって、これはこれで面白い。

サブエージェント・カスタムスラッシュコマンド・Skills の関係を整理するとこうなる。

| 機能 | 配置場所 | 自分で書く？ | 主な用途 |
|---|---|---|---|
| サブエージェント | `.claude/agents/{name}.md` | 自作 | 独自の役割を持ったエージェント |
| カスタムスラッシュコマンド | `.claude/commands/{name}.md` | 自作 | 自作エージェントへの薄いラッパー、よく使う指示の固定化 |
| Skills（組み込み） | Claude Code 本体 / プラグイン | 既製品 | プロジェクト初期化、レビュー、繰り返し実行などの汎用機能 |

呼び出し方は **3 つともプロンプト欄で `/` を打つ**点で共通している。使う側からは区別なく見えるが、中身が「自作」か「組み込み」かが違う。

ちなみに、カスタム Skill を自作することもできる（`~/.claude/skills/` に置く形式）。ここまでくると公式ドキュメントを参照したほうが早いので深追いしないが、「サブエージェントとは別に Skills を自作する道もある」と覚えておくと、後で必要になったときに調べやすい。

省力化のコツとして、**自作する前にまず Skills で代替できないか確認する**。これだけで、書かなくていいものを書く時間がだいぶ減る。

## 6. 3 つを組み合わせた執筆ワークフロー

ここまでの 3 つを実際にどう組み合わせて使っているかを書く。

1. **構成案を作る**: `/09_insight_extractor 〇〇について書きたい`（自作サブエージェント + カスタムスラッシュコマンド）
2. **構成案を人間がレビュー**: タイトル候補を選び、章の順序や抜け漏れを直す
3. **本文を執筆する**: `/07_tech_writer {構成案ファイルのパス}`（自作サブエージェント + カスタムスラッシュコマンド）
4. **記事をレビューする**: `/review`（組み込み Skills）
5. **人間が最終調整**して `zenn push`

ポイントは 4 のところで、ここは Skills に任せている。レビュー専用のサブエージェントを自作することもできるけれど、組み込みの `/review` で十分だった。

「自作」と「組み込み」を組み合わせるのがちょうどいい、というのがやってみた結論だ。全部自作しようとすると消耗するし、全部組み込みで済ませようとすると自分のドメイン特有の役割が表現できない。境界線をどこに引くかは、しばらく使いながら調整していくしかない。

## 7. やってみてわかったこと（学びの整理）

初心者の自分が触って素直に思ったことをいくつか。

- `.claude/agents/` は本当に「ファイルを置くだけ」で動く。再起動も登録作業も要らないので、最初に動いたときは少し驚いた。
- 一番ハマったのは、**サブエージェントの `name` フィールドとファイル名の対応**だ。最初は別名でも動くと思っていて、なぜか呼び出せず悩んだ。`name` とファイル名（拡張子を除いた部分）は揃えておくのが無難。
- Skills の存在に気づいたのが後半だった。先に `/` を眺めていれば、レビュー用のサブエージェントを書きかけて消す、みたいな手戻りが減ったはず。
- `.claude/settings.json` と `.claude/settings.local.json` の使い分けは、**チームで共有したい設定は前者、個人のローカル設定（API キーやパス）は後者**、と覚えるとシンプル。後者は `.gitignore` に入れておく。

限界・注意点として正直に書いておくと、

- サブエージェントの「禁止事項」はあくまでソフトな制約で、たまにすり抜ける。たとえば構成案担当が、章のキーメッセージとして 1〜2 文の本文っぽいものを書いてくることがある。重要な禁止事項は system prompt の冒頭と末尾の両方に書くとマシになる体感がある。
- Claude Code はバージョンが上がると挙動や利用できる Skills が変わる可能性がある。書いてある内容も自分の手元で確かめながら進めたほうがいい。
- サブエージェントを増やしすぎると、`/` 補完がにぎやかになって選択コストが上がる。役割が被ってきたら統合する判断もある。

## 8. まとめと次に学びたいこと

`.claude/` 配下は「自作の Markdown を数枚置くだけで動く」気軽さがある。難しい仕組みを覚える前に、まずは 1 ファイル置いて挙動を見てみるのがいい。

順番としては、

1. `/` を打って、組み込みの Skills で何ができるかを眺める
2. 足りない役割があれば、`.claude/agents/` にサブエージェントを書く
3. 呼び出しが面倒になってきたら `.claude/commands/` でカスタムスラッシュコマンドを足す

の流れがしっくりきた。最初から全部設計しようとせず、必要になったら次の段に進む、くらいで十分動く。

次に試したいと思っているのは、

- `.mcp.json` で MCP サーバーをつなぐ設定
- フックの設定（pre-commit、post-tool-use など）
- `.claude/settings.json` をチームで共有する運用

このあたりを触ったらまた書く。`.claude/` をブラックボックスのまま使っている人の参考になれば。
