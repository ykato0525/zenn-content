Claude Code を使い始めて少し経つのですが、`.claude/` というフォルダが何のためにあるのか、長らくよくわかっていませんでした。サブエージェント、スラッシュコマンド、Skills、settings.json、それぞれ名前は聞いたことがあるのですが、自分のプロジェクトでどう配置すれば何が起きるのかがピンと来ません。

とりあえず動かすか！でいろいろやってみました。

Zenn 記事を書きたいというモチベーションを起点に、`.claude/` の中身を一つずつ触ってみました。やってみたら、サブエージェントもスラッシュコマンドも Skills も、想像していたよりずっと素朴な仕組みで、Markdown を数枚置くだけで動きます。せっかくなので、同じところで詰まっている方の最短ルートになるよう、触ってわかったことを順番に書き残しておきます。

## 1. ゴール

最終的にできたのは、Zenn 記事を書くときに次の3つのスラッシュコマンドを順番に叩けば一通り回る、という状態です。

- `/09_insight_extractor`: 記事の構成案（タイトル候補・フック・章立て）を作るサブエージェントを呼び出します
- `/07_tech_writer {構成案ファイル}`: 構成案に沿って本文を執筆するサブエージェントを呼び出します
- `/review`: 書き上がった内容を Claude Code 組み込みの Skill でレビューしてもらいます

Claude Code のプロンプト欄で `/` を打つと、自分が定義したスラッシュコマンドと、組み込みの Skills がずらっと候補として並びます。設定したのは `.claude/` 配下に Markdown を数枚置いただけで、本体の機能は何もいじっていません。これだけで「次は何を叩くか」が画面の上で完結するようになりました。

ここまでの設定の流れを、後の章で順番にほどいていきます。

## 2. `.claude/` フォルダの正体を整理する

最初にハマったのは、そもそも `.claude/` 配下のファイルが「誰が・いつ・どう解釈するのか」がわからなかったことでした。サブエージェントは知っているのですが、`commands/` というフォルダもありますし、`settings.json` と `settings.local.json` の使い分けもわかりません。

触ってみてやっと理解できた全体像はこうなりました。

| パス | 役割 | 誰が解釈するか |
|---|---|---|
| `.claude/agents/{name}.md` | サブエージェント定義 | Claude Code が認識して呼び出す |
| `.claude/skills/<name>/SKILL.md` | カスタム skill（自作スラッシュコマンド、新仕様） | Claude Code が `/` 入力時に検出 |
| `.claude/commands/{name}.md` | カスタムコマンド（旧仕様、`.claude/skills/` の後方互換） | 同上 |
| `.claude/settings.json` | プロジェクトレベル設定（チームで共有） | Claude Code 起動時 |
| `.claude/settings.local.json` | 個人ローカル設定（自動 gitignore） | 同上 |
| `~/.claude/` | ユーザー全体の設定（プロジェクト横断） | Claude Code |
| bundled skills / built-in commands | 組み込み機能（`/init` `/review` `/loop` など） | Claude Code |

ポイントは、**「自分で配置するファイル」と「Claude Code 本体に組み込まれた機能」は別物**だ、ということでした。私は最初、`/review` のような便利コマンドも自分で定義しないと使えないと思い込んでいて、そのせいで「何から書けばいいんだ」と固まっていました。実際は、組み込みの Skills だけでもかなり多くのことができます。

この全体像をうっすらでも握ってから、サブエージェント → カスタムスラッシュコマンド → Skills の順に触っていったら、迷子になる時間がだいぶ減りました。以降の章はその順番でなぞっていきます。

## 3. サブエージェント (`.claude/agents/`) を触ってみる

最初に試したのがサブエージェントでした。「専用の役割を持った Claude を別コンテキストで動かせる」と聞いて、難しそうな気がしていたのですが、実体は YAML frontmatter 付きの Markdown ファイルを 1 枚置くだけでした。

たとえば構成案を作る担当のサブエージェントは、こう書いてみました。

```markdown
---
name: 09_insight_extractor
description: 気づきを抽出してZenn投稿案（タイトル・フック・章立て）を作成。本文執筆は禁止。
---

# Insight Extractor エージェント

## 役割
気づきを抽出して Zenn の投稿案（構成案）を作る。

## 出力
- markdown ファイル: タイトル候補、フック、章立て、キーメッセージ

## 禁止事項（厳守）
- 記事本文の執筆（タイトル・フック・構成まで）
- 投稿の実行
```

これを `.claude/agents/09_insight_extractor.md` として保存するだけで、Claude Code が認識してくれます。同じパターンで本文執筆担当の `07_tech_writer.md` も配置しました。

触ってみてわかった大事なことが二つあります。

ひとつは、**サブエージェントは独立したコンテキストで動く**ことです。メイン会話の履歴を引きずらないので、メインで雑談していても、サブエージェントは新鮮な状態で仕事を始めてくれます。これは思ったより便利でした。

もうひとつは、**「禁止事項」を書いておくと役割境界が安定する**ことです。Claude は得意なことを勝手にやろうとするので、構成案担当に「本文の執筆禁止」と明記しておかないと、章のキーメッセージとして 1〜2 文の本文っぽいものを書いてきてしまいます。明文化することで、出力がだいぶ落ち着きました。

## 4. スラッシュコマンド (`.claude/commands/`) で呼び出しを楽にする

サブエージェントは置いただけで使えるのですが、メイン会話から呼び出すには「`09_insight_extractor` サブエージェントを使って…」と毎回書く必要があります。これがすぐに面倒になりました。

そこで `.claude/commands/{name}.md` に薄いラッパーを置いてみました。

```markdown
---
description: ⑦Tech Writer — Zenn 記事執筆エージェントを起動
argument-hint: [構成案ファイルのパス]
---

`07_tech_writer` サブエージェントを使って次の依頼を処理してください。サブエージェントの責務・禁止事項を必ず守ること。

依頼内容: $ARGUMENTS
```

これだけで、プロンプト欄に `/07_tech_writer data/insight_drafts/xxx.md` と打てばサブエージェントが起動します。`$ARGUMENTS` にはスラッシュの後ろに書いた文字列がそのまま入ります。

地味に効くのが `argument-hint` です。スラッシュコマンドを補完で選ぶときにヒントとして表示されるので、自分で何の引数を渡せばいいか忘れずに済みます。サブエージェントを増やしていくと「どのコマンドが何を期待するんだっけ」になりがちなので、これは早めに書く癖をつけておくとよさそうです。

サブエージェントとカスタムスラッシュコマンドを 1 ペアずつ作っただけで、執筆フローは「`/09_insight_extractor` → 構成レビュー → `/07_tech_writer`」と、3 ステップに圧縮されました。

## 5. Skills を発見した（`/init` `/review` `/security-review` ...）

Tech Writer まで作って一息ついたところで、ふと `/` を入力したときの補完を眺めていたら、自分が定義していないスラッシュコマンドが大量に並んでいることに気づきました。`/init` `/review` `/security-review` `/simplify` `/loop` `/schedule` などなどです。

これが Skills でした。Skills は **Claude Code の拡張機構の総称**で、最初から使える bundled skills（`/simplify` `/loop` など）と、自分で書く user / project skills、それから `/init` `/review` のような built-in command まで `/` 補完にまとめて並びます。`.claude/` を空っぽにしていても、bundled skills と built-in commands はすぐに使えるようになっています。

私が触ってみて便利だったものを挙げると、

- `/init`: プロジェクトを初めて開いたときに `CLAUDE.md` を生成してくれます
- `/review`: コードや記事の差分をレビューしてくれます
- `/security-review`: セキュリティ観点のレビューを走らせてくれます
- `/loop`: 同じプロンプトを定期的に繰り返し実行します
- `/schedule`: Routines（クラウド側で動く定期実行タスク）を CLI から管理します

サブエージェントを書く前にこれを見ていたら「自分で書くまでもない仕事」がいくつもありました。とくに `/review` は、自作の Tech Writer に書かせた記事の最終チェックにそのまま使えて、わざわざレビュー専用のサブエージェントを作る必要はありませんでした。

ちなみにこの記事自体も、Tech Writer サブエージェントに書いてもらった本文を、人間がちょこちょこ手で直したものです。書きながら同時にデバッグしている感覚があって、これはこれで面白い体験でした。

サブエージェント、カスタム skill / カスタムコマンド、bundled skills / built-in commands の関係を整理するとこうなります。

| 機能 | 配置場所 | 自分で書く？ | 主な用途 |
|---|---|---|---|
| サブエージェント | `.claude/agents/{name}.md` | 自作 | 独自の役割を持ったエージェント |
| カスタム skill（新仕様） | `.claude/skills/<name>/SKILL.md` | 自作 | 自作エージェントへの薄いラッパー、よく使う指示の固定化 |
| カスタムコマンド（旧仕様） | `.claude/commands/{name}.md` | 自作 | 上と同じ用途。後方互換のため残っている形式 |
| bundled skills | Claude Code 本体 / プラグイン | 既製品 | `/simplify` `/loop` `/batch` など組み込み済みの skill |
| built-in commands | Claude Code 本体 | 既製品 | `/init` `/review` `/security-review` など固定ロジックのコマンド |

公式ドキュメントには **「Custom commands have been merged into skills」** とあり、`.claude/commands/{name}.md` は今も動くものの、新規には `.claude/skills/<name>/SKILL.md` 形式が推奨されています。`/` 補完にはこれらすべてが並ぶので、使う側からは区別なく見えます。中身が「自作」か「組み込み」かが違うだけです。

ちなみに、カスタム skill を自作することもできます。`~/.claude/skills/<skill-name>/SKILL.md` のように **ディレクトリを 1 つ作って、その中に `SKILL.md` を置く**形式です（プロジェクト共有なら `.claude/skills/<skill-name>/SKILL.md`）。ファイル直置きではなくディレクトリ単位なので、補助ファイルやスクリプトを同じディレクトリに同梱できるのが利点です。ここまで来ると公式ドキュメントを参照したほうが早いので深追いしませんが、「サブエージェントとは別に skill を自作する道もある」と覚えておくと、後で必要になったときに調べやすいと思います。

省力化のコツとして、**自作する前にまず Skills で代替できないか確認するのがおすすめ**です。これだけで、書かなくていいものを書く時間がだいぶ減ります。

## 6. 3 つを組み合わせた執筆ワークフロー

ここまでの 3 つを実際にどう組み合わせて使っているかを書いておきます。

1. **構成案を作る**: `/09_insight_extractor 〇〇について書きたい`（自作サブエージェント + カスタムスラッシュコマンド）
2. **構成案を人間がレビューする**: タイトル候補を選び、章の順序や抜け漏れを直す
3. **本文を執筆する**: `/07_tech_writer {構成案ファイルのパス}`（自作サブエージェント + カスタムスラッシュコマンド）
4. **記事をレビューする**: `/review`（組み込み Skills）
5. **人間が最終調整**して `zenn push`

ポイントは 4 のところで、ここは Skills に任せています。レビュー専用のサブエージェントを自作することもできるのですが、組み込みの `/review` で十分でした。

「自作」と「組み込み」を組み合わせるのがちょうどいい、というのがやってみた結論です。全部自作しようとすると消耗しますし、全部組み込みで済ませようとすると自分のドメイン特有の役割が表現できません。境界線をどこに引くかは、しばらく使いながら調整していくしかないかなと思っています。

## 7. やってみてわかったこと（学びの整理）

初心者の自分が触って素直に思ったことをいくつか書いておきます。

- `.claude/agents/` は本当に「ファイルを置くだけ」で動きます。再起動も登録作業も要らないので、最初に動いたときは少し驚きました。
- 一番ハマったのは、**サブエージェントの `name` フィールドとファイル名の対応**でした。最初は別名でも動くと思っていて、なぜか呼び出せず悩みました。`name` とファイル名（拡張子を除いた部分）は揃えておくのが無難です。
- Skills の存在に気づいたのが後半でした。先に `/` を眺めていれば、レビュー用のサブエージェントを書きかけて消す、みたいな手戻りが減ったはずです。
- `.claude/settings.json` と `.claude/settings.local.json` の使い分けは、**チームで共有したい設定は前者、個人のローカル設定（API キーやパス）は後者**、と覚えるとシンプルです。後者は `.gitignore` に入れておきます。

限界・注意点として正直に書いておくと、

- サブエージェントの「禁止事項」はあくまでソフトな制約で、たまにすり抜けてしまいます。たとえば構成案担当が、章のキーメッセージとして 1〜2 文の本文っぽいものを書いてくることがあります。重要な禁止事項は system prompt の冒頭と末尾の両方に書くとマシになる体感があります。
- Claude Code はバージョンが上がると挙動や利用できる Skills が変わる可能性があります。書いてある内容も自分の手元で確かめながら進めたほうがよさそうです。
- サブエージェントを増やしすぎると、`/` 補完がにぎやかになって選択コストが上がってしまいます。役割が被ってきたら統合する判断もありそうです。

## 8. まとめと次に学びたいこと

`.claude/` 配下は「自作の Markdown を数枚置くだけで動く」気軽さがあります。難しい仕組みを覚える前に、まずは 1 ファイル置いて挙動を見てみるのがおすすめです。

順番としては、

1. `/` を打って、bundled skills と built-in commands で何ができるかを眺める
2. 足りない役割があれば、`.claude/agents/` にサブエージェントを書く
3. 呼び出しが面倒になってきたら `.claude/skills/<name>/SKILL.md` でカスタム skill を足す（旧形式の `.claude/commands/{name}.md` も今のところ動きます）

の流れがしっくり来ました。最初から全部設計しようとせず、必要になったら次の段に進む、くらいで十分動きます。

次に試したいと思っているのは、

- `.mcp.json` で MCP サーバーをつなぐ設定
- フックの設定（pre-commit、post-tool-use など）
- `.claude/settings.json` をチームで共有する運用

claude codeを使ってみたいけど、どうしたら・・・という人の参考になれば幸いです！！
